# Web 画面（ブラウザからの実行・設定）

クライアント PC のブラウザから、GB10 上の runner を実行・停止し、進捗のログと生成物を確認できる。
スキルの登録、対象フォルダ・出力先フォルダの選択、対象の設定（targets.toml）の編集、毎日の定期実行の設定も画面から行える。

```
クライアント PC（ブラウザ）            サーバー(GB10)
  http://192.168.31.26:4000  ───>  Web 画面（python -m godoc_agent.web、常駐）
                                      └─ runner を別プロセスで起動 ── Claude Code ── Ollama
```

ソースコードと設計書の生成処理は、これまでどおりサーバーの中だけで行う。ブラウザに送るのは、画面の表示に必要なもの（ログ、生成物の本文、フォルダ名）だけ。

## 1. できること・権限

| 操作 | ログインなし | 管理者（パスワードでログイン） |
|---|---|---|
| 状態・ログ・実行履歴・生成物の閲覧、生成物のダウンロード | ○（`WEB_VIEW_REQUIRES_LOGIN=true` なら ×） | ○ |
| 対象の設定の閲覧 | ○（同上） | ○ |
| 実行・停止 | × | ○ |
| 対象フォルダ・出力先フォルダの選択（フォルダ選択ダイアログ） | × | ○ |
| 対象の設定の変更・対象ファイルのプレビュー | × | ○ |
| スキルの登録・確認・直前に戻す・登録を外す | × | ○（「スキル」タブは管理者にだけ表示） |
| 定期実行の設定（オン/オフ・時刻・スキル・git pull） | 閲覧だけ | ○ |

管理者は1種類だけで、パスワードを知っている人が管理者になる。ユーザーごとのアカウントはない。

### 実行の競合を防ぐ仕組み

- Web 画面から同時に動かせる runner は1つだけ。実行中は「実行」ボタンが押せず、API に直接送っても `409` で断る
  - runner の中では、Claude Code のセッション（1ファイル×1タスク = 1セッション）を最大10個まで並列に動かせる（[セッションの監視](#セッションの監視)）
- runner 本体も、出力先フォルダごとにロック（`<出力先>/.runner.lock`）を取る。夜間タイマー・コマンド・Web 画面のどこから起動しても、同じ出力先では同時に1つしか動かない。後から起動した方は `エラー: 別の実行が進行中です` で止まる（終了コード `2`）
  - 夜間タイマーが動いている間は、画面の状態に「他の実行が進行中（夜間バッチ・コマンド）」と表示され、実行ボタンは押せない
  - 出力先が違う実行どうしは同時に動ける（データは壊れないが、Ollama を取り合うので遅くなる）。夜間タイマーと同じ出力先（既定 `/opt/Lang_Chain/out`）を選んでおくと確実に排他できる
- 実行中は設定（フォルダ・スキル・対象の設定）を変更できない。どの設定で動いた結果か分からなくなるのを防ぐため

### 停止

「停止」を押すと、runner と、runner が起動した claude をまとめて止める（30 秒たっても止まらなければ強制終了する）。
完了済みのファイルは manifest に記録されているので、もう一度「実行」を押すと残りのファイルだけが最初から処理される。

## 2. 設置（初回だけ）

すでに設計書の生成（コマンド・夜間タイマー）が動いているサーバーに追加する場合は、[migration_web_ui.md](migration_web_ui.md) の手順で行う（夜間タイマーからの切り替え・GitLab の認証・元に戻す方法を含む）。

```bash
ssh gb10
cd /opt/Lang_Chain
git pull
.venv/bin/pip install -r requirements.txt     # fastapi・uvicorn が追加された

# 1. 管理者パスワードを決め、ハッシュを .env に書く（パスワード自体はどこにも保存されない）
.venv/bin/python -m godoc_agent.web.password  # 12文字以上。表示された WEB_ADMIN_PASSWORD_HASH=... の行を .env に追記
#    （`>> .env` でリダイレクトしてもよい。入力の確認は画面に出る）

# 2. 残りの設定を .env に追記する（値は環境に合わせる）
#    CLAUDE_BIN は `which claude` のフルパスにしておく（systemd から起動すると PATH に ~/.local/bin が入らない）
#    WEB_BROWSE_ROOTS に書くフォルダは先に作っておく（ないと起動しない）
mkdir -p /opt/Lang_Chain/out
cat >> .env <<'EOF'
WEB_HOST=0.0.0.0
WEB_PORT=4000
WEB_BROWSE_ROOTS=/srv/repos,/opt/Lang_Chain/out
EOF

# 3. 手動で起動して確かめる（Ctrl+C で止める）
.venv/bin/python -m godoc_agent.web
#    クライアント PC のブラウザで http://192.168.31.26:4000 を開く

# 4. 常駐させる（sudo が必要。自分のターミナルから ssh -t gb10 で実行する）
sudo cp deploy/systemd/godoc-web.service /etc/systemd/system/
sudo sed -i "s/REPLACE_WITH_USER/$USER/" /etc/systemd/system/godoc-web.service
sudo systemctl daemon-reload
sudo systemctl enable --now godoc-web.service
systemctl status godoc-web.service            # active (running) ならよい
```

ファイアウォール（ufw）を使っている場合は、LAN からだけ 4000 番を開ける。

```bash
sudo ufw allow from 192.168.31.0/24 to any port 4000 proto tcp
```

### 設定項目（.env）

| 項目 | 必須 | 内容 |
|---|---|---|
| `WEB_ADMIN_PASSWORD_HASH` | 必須 | 管理者パスワードのハッシュ。`python -m godoc_agent.web.password` で作る。パスワードを変えるときも同じ手順で作り直し、Web 画面を再起動する |
| `WEB_BROWSE_ROOTS` | 必須 | フォルダ選択ダイアログで辿れる起点（カンマ区切りの絶対パス）。対象・出力先はこの下からしか選べない。広くしすぎない（例：`/srv/repos,/opt/Lang_Chain/out`） |
| `WEB_HOST` | 任意 | 待ち受けるアドレス。既定 `127.0.0.1`（GB10 自身からだけ）。LAN から使うなら `0.0.0.0` |
| `WEB_PORT` | 任意 | 既定 `4000` |
| `WEB_SESSION_TTL_HOURS` | 任意 | ログインの有効時間。既定 `12` |
| `WEB_VIEW_REQUIRES_LOGIN` | 任意 | `true` にすると閲覧にもログインが必要。既定 `false` |
| `WEB_COOKIE_SECURE` | 任意 | HTTPS で使う場合は `true`。既定 `false` |
| `WEB_STATE_DIR` | 任意 | 画面で選んだフォルダの保存先。既定 `/opt/Lang_Chain/state/web` |

設定の誤り（ハッシュの形式、`WEB_BROWSE_ROOTS` のフォルダがないなど）があると、`エラー: ...` を表示して起動しない。

## 3. 使い方

1. ブラウザで `http://192.168.31.26:4000` を開き、右上から管理者パスワードでログインする
2. **スキル**タブで設計書スキルを登録する（初回だけ。すでに `skills/design-doc-batch/` に置いてあれば「登録済み」と表示される）
   - 「フォルダを選んで登録」… SKILL.md のあるフォルダを選ぶと、参照ファイル（`references/` など）ごと登録する
   - 「SKILL.md だけ登録」… SKILL.md 1ファイルだけを登録する
   - コメント追記も行う場合は、コメント追記スキルも登録する（登録するとタスクに「コメント追記」が出る）
3. **実行**タブの「フォルダ」で、対象フォルダ（`--repo`）と出力先（`--out`）を「選択…」から選ぶ
   - 出力先は、ダイアログ下の「新しいフォルダ名」に名前を入れると、選んでいるフォルダの下に新しいフォルダを指定できる（実行時に作られる）
   - 出力先を対象フォルダの中にはできない（生成物が次回の対象に混ざるため）
4. **対象の設定**タブで、言語・対象（include）・除外（exclude）を確認する。「対象ファイルを確認」で、保存前の設定でどのファイルが処理されるかを一覧できる。変えたら「保存」
5. **実行**タブで、スキル（プルダウンで複数選べる）・件数の上限・同時セッション数（1〜10。初期値は `.env` の `LLM_CONCURRENCY`）・再生成を選んで「実行」。ログが流れ、終わると状態・実行履歴・生成物が更新される
6. 生成物の一覧からファイルを選ぶと本文が表示される。「ダウンロード」で保存できる

手動の実行で「実行前に対象フォルダを git pull する」を選ぶと、対象フォルダを `git pull --ff-only` してから実行する（失敗したら生成しない）。

### セッションの監視

「実行」タブの **セッション** 欄に、表示中の実行（実行中のもの、または実行履歴で選んだもの）の Claude Code のセッションの状況が出る（2秒ごとに更新）。

- **占有メーター**：1マス = 1セッション枠。処理中の枠が色付きになり、右上に `使用中 3 / 10`・`完了 12 / 40 件 ・ 待ち 25 件` が出る
- **枠ごとのカード**（S01〜S10）：実行中 / 空き、処理中のファイル・スキル・何回目の生成か・経過時間、最後の出来事
- カードを押すと、その枠の **セッションログ**（開始・生成の開始と完了・検証OK/NG・終了の直近50件）が下に出る。もう一度押すと閉じる
- runner が強制終了などで終了を書き出せなかった場合、処理中だった枠は「中断」と表示する
- 同じ出来事は、全体のログにも `[S03] 生成 2/3 回目を開始` の形で出る。記録は `<出力先>/_runs/<run_id>.sessions.json`（夜間バッチ・コマンドからの実行も同じ）

同時セッション数を増やしても、Ollama が同時に処理する数（`OLLAMA_NUM_PARALLEL`）より多い分は Ollama 側で待つだけで速くならない。
10 並列にする場合は Ollama 側も `OLLAMA_NUM_PARALLEL=10` にし、KV キャッシュ（コンテキスト長 × 並列数に比例）が GPU メモリに収まるかを `ollama ps` で確かめる（[performance_troubleshooting.md](performance_troubleshooting.md)）。
定期実行は `.env` の `LLM_CONCURRENCY` で動く。

### 定期実行（毎日決まった時刻に実行する）

**実行**タブの「定期実行」で設定する。Web 画面（godoc-web.service）が常駐していれば、毎日その時刻に、画面で選んでいる対象フォルダ・出力先で実行する。

| 項目 | 内容 |
|---|---|
| 毎日実行する | オン/オフ |
| 時刻 | サーバー（GB10）の時刻。既定 02:00 |
| スキル | 登録済みのスキルをプルダウンで複数選ぶ。保存した後で登録を外したスキルは、実行時に除く |
| 実行前に git pull | 対象フォルダを `git pull --ff-only` してから実行する。失敗したら生成しない（古いソースから設計書を作らないため）。条件は下の「実行前の git pull」を参照 |

- 1日に1回だけ実行する。実行時刻に Web 画面が止まっていた場合は、起動したときにその日の分を実行する
- 実行時刻に別の実行（手動・コマンド）が動いていれば、終わるのを待ってから実行する
- 保存した時点で今日の時刻を過ぎていれば、今日の分は実行せず翌日から実行する（まだ来ていなければ、今日の新しい時刻に実行する）
- フォルダ未設定などで開始できなかった場合は、画面の「前回」に理由が表示され、翌日に再び試す
- run_id は `scheduled-<日時>`。実行履歴・ログは手動の実行と同じように見られる。開始・失敗はサーバーのログ（`journalctl -u godoc-web.service`）にも残る
- 設定は `state/web/schedule.json` に保存される
- git pull は Web 画面の実行ユーザー（godoc-web.service の `User=`）で行う。そのユーザーで、パスワード入力なしで `git pull` できるようにしておく（SSH 鍵・デプロイキーなど）

### 実行前の git pull

手動の実行・定期実行で「実行前に git pull」を選ぶと、runner の前に `git -C <対象フォルダ> pull --ff-only` を実行する。
プログラムはリポジトリ名や URL を持っておらず、pull 先は git が対象フォルダの `.git/config`（`git clone` したときに書かれたクローン元の URL と、ブランチの追跡先）から決める。GitLab でも GitHub でも同じ。

意図しないリポジトリを pull しないよう、pull の前に次を確かめ、満たさなければ pull も生成もしない（「実行」ボタン・定期実行の保存のときにも確かめて、画面にエラーを出す）。

| 確認 | 満たさない例 |
|---|---|
| 対象フォルダが、クローンしたリポジトリの**最上位フォルダ**であること | クローンの中のサブフォルダを選んだ / git 管理されていない親フォルダ（複数の `xx_api` をまとめたフォルダ）を選んだ。git は `.git` がないと親フォルダをたどるため、上位に別のリポジトリがあるとそれを pull してしまう |
| ブランチを取り出していること | 特定のコミットを取り出している（detached HEAD） |
| ブランチに pull 先（追跡ブランチ）が設定されていること | `git init` しただけ・リモートを設定していない |

pull の前に、pull 先の URL・追跡ブランチ（例：`origin/main`）・リポジトリのフォルダをログに出す。URL に含まれる認証情報（`https://oauth2:<トークン>@...` など）は `***` に伏せる。

pull はパスワード入力なしで通る必要がある（入力待ちで止まらないよう、git に尋ねさせない）。GitLab の場合は次のどちらかを、Web 画面の実行ユーザー（godoc-web.service の `User=`）に設定しておく。

- SSH（推奨）：プロジェクトに読み取り専用の**デプロイキー**を登録し、実行ユーザーの `~/.ssh` に秘密鍵を置く。初回は `ssh -T git@<GitLabのホスト>` で `known_hosts` に登録しておく
- HTTPS：`read_repository` 権限の**プロジェクトアクセストークン**を、実行ユーザーの credential helper に保存する

確認方法：`sudo -u <実行ユーザー> git -C <対象フォルダ> pull --ff-only` がパスワードを聞かれずに成功すればよい。
複数の `xx_api` を別々にクローンしてまとめた親フォルダを対象にする場合は、「実行前に git pull」をオフにし、別の方法でそれぞれを更新する。

**systemd の夜間タイマーから移行する場合**は、二重に実行しないよう、systemd のタイマーを止めてから画面で定期実行を有効にする。

```bash
ssh -t gb10 "sudo systemctl disable --now godoc-nightly.timer"
systemctl list-timers godoc-nightly.timer   # 表示されなければ止まっている
```

画面では、対象フォルダを夜間タイマーの `GODOC_REPO`、出力先を `GODOC_OUT`（既定 `/opt/Lang_Chain/out`）と同じにすると、これまでの設計書・差分スキップの記録を引き継げる。

### スキルの保存先

画面から登録したスキルは、runner が読む場所にそのまま置かれる。夜間タイマー・コマンドからの実行でも同じスキルが使われる。

| スキル | 保存先 | 出力先 |
|---|---|---|
| 設計書（`doc`） | `CLAUDE_SKILL_PATH` のフォルダ。未設定なら `skills/design-doc-batch/` | `<出力先>/` 直下 |
| コメント追記（`comment`） | `CLAUDE_COMMENT_SKILL_PATH` のフォルダ。未設定なら `skills/comment-batch/` | `<出力先>/_commented/` |
| 追加のスキル | `skills/<スキル名>/`（名前と出力の種類は `skills/registry.json`） | `<出力先>/_<スキル名>/` |

### スキルの追加（設計書・コメント追記以外）

「スキル」タブの「スキルを追加」で、スキル名と出力の種類を決めて、フォルダまたは SKILL.md を選ぶ。
追加したスキルは、「実行」タブと定期実行の「スキル」プルダウンで選べる（複数選ぶと1回の実行でまとめて処理する）。
コマンドからの実行でも `--tasks doc,<スキル名>` のように名前で指定できる。

| 出力の種類 | 出力（ファイルごと） | 検証 | 前回の出力 |
|---|---|---|---|
| 文書（Markdown） | `<出力先>/_<スキル名>/<相対パス>.md` | 本文が空でないこと | 引き継いで改訂させる |
| コメントだけ変更したソース | `<出力先>/_<スキル名>/<相対パス>` | コメント以外のコードが変わっていないこと（コメント追記と同じ） | 引き継がない |
| コードも変更したソース | `<出力先>/_<スキル名>/<相対パス>` | 本文が空でないことだけ（正しさは機械的に判定できない） | 引き継がない |

- スキル名は英小文字・数字・`-`・`_`（40文字以内、英小文字か数字で始める）。`doc`・`comment`・`runs` などは予約されていて使えない
- 対象リポジトリはどの種類でも書き換えない。ソースを出力するスキルの結果を取り込むかどうかは、差分を見て人が判断する
- 同じ名前で登録し直すと、スキルが入れ替わる（出力の種類は省略すれば前のまま）
- 追加のスキルの「登録を外す」は、一覧から消し、フォルダを `skills/<スキル名>.prev` に移す。出力済みのファイルは消さない

- 登録すると、直前のスキルは `<フォルダ名>.prev` に1世代だけ残る。「直前に戻す」で入れ替えられる
- コメント追記スキルの「登録を外す」は、フォルダを `.prev` に移す。コメント追記は実行されなくなる（「直前に戻す」で戻せる）
- `skills/comment-batch/SKILL.md` があれば、`.env` に `CLAUDE_COMMENT_SKILL_PATH` を書かなくてもコメント追記を行う（この版からの変更）
- 上限：1スキルあたり 200 ファイル・合計 10MB・1ファイル 2MB。SKILL.md は UTF-8 で、フォルダの直下に必要

### 対象の設定の保存先

`TARGETS_CONFIG`、未設定なら `/opt/Lang_Chain/targets.toml` に保存する（runner が読む場所と同じ）。
`targets.toml` がない間は例の設定（targets.example.toml）が表示され、保存すると `targets.toml` が作られる。
検証は runner と同じ処理で行うので、書き方の誤りは保存時にエラーとして表示される（保存されない）。
画面から保存すると、ファイル内のコメントは消える。書き方の詳細は [target_files.md](target_files.md) を参照。

## 4. 運用

| 作業 | 方法 |
|---|---|
| 状態の確認 | `systemctl status godoc-web.service` / `journalctl -u godoc-web.service -n 50` |
| 再起動（`.env` を変えたとき、`git pull` で更新したとき） | `sudo systemctl restart godoc-web.service` |
| パスワードの変更 | `python -m godoc_agent.web.password` で作り直して `.env` を書き換え、再起動 |
| 実行のログ | 画面のほか、`<出力先>/_runs/web-<日時>.log` に残る（計測ログは同じ名前の `.jsonl`、セッションの状況は `.sessions.json`） |

- Web 画面を再起動すると、ログイン状態は消える（もう一度ログインする）
- 再起動しても、画面で選んだフォルダは `state/web/workspace.json` に残る
- Web 画面を止める（再起動する）と、実行中の runner も止まる（`KillMode=control-group`）。完了済みのファイルは manifest に残るので、再実行で続きから処理される

## 5. セキュリティ上の注意

- **通信は HTTP（暗号化なし）**。同じ LAN 上で通信を盗聴できる人には、パスワード・設計書の本文が見える。信頼できない人がいるネットワークでは次のどちらかにする
  - SSH トンネル：`WEB_HOST=127.0.0.1` のままにし、クライアントで `ssh -N -L 4000:127.0.0.1:4000 gb10` を実行してから `http://localhost:4000` を開く
  - HTTPS のリバースプロキシ（nginx・Caddy など）を前に置き、`WEB_COOKIE_SECURE=true` にする
- 閲覧は既定でログイン不要。設計書の内容を LAN 内の誰にも見せたくない場合は `WEB_VIEW_REQUIRES_LOGIN=true` にする
- ログインに5回続けて失敗した接続元は、15分間ログインできなくなる
- フォルダ選択ダイアログは `WEB_BROWSE_ROOTS` の外を表示しない。生成物の表示は出力先の中のファイルだけで、`_runs/` やドットファイル（`.manifest.json` など）は表示しない
- 状態を変える操作（ログイン・実行・設定変更）には専用のヘッダーを必須にし、Cookie は `SameSite=Strict`・`HttpOnly` にしている（別のサイトから操作を送り込まれるのを防ぐため）

## 6. 既知の制約

- 管理者は1人分（パスワード1つ）。誰が実行したかは記録しない
- ログイン状態はサーバーのメモリに持つため、Web 画面を複数プロセスで動かす構成には対応しない（1プロセスで動かす）
- 出力先が違えば、systemd の夜間タイマーと Web 画面からの実行が同時に動きうる（「実行の競合を防ぐ仕組み」を参照）。画面の定期実行に移行した場合はこの心配はない
- 定期実行は Web 画面が動いている間だけ動く。godoc-web.service を止めている間に時刻を過ぎた場合は、その日のうちに起動すれば実行し、翌日以降に起動した場合は過ぎた日の分は実行しない
- 定期実行は1種類（1つの時刻・1組のフォルダ）だけ。手動の実行と同じフォルダを使う
- 対象フォルダに選べるのはサーバー上のフォルダだけ。NAS 上のフォルダは、サーバーにマウントしてから選ぶ（[nas_target.md](nas_target.md)）
